### 1. RAG 里面的三种排序 / 召回方式



#### 1.1 粗排（召回）阶段

-----------

###### ① 稠密检索排序（双塔 Embedding）

* 方式：query 向量 和 预存的文档向量算**余弦相似度**，分数从高到低排序，取 top‑k
* 模型：BGE‑large‑zh 这类 embedding 模型（双塔模型）
* 特点：速度快，文档向量可以提前入库；语义能力尚可，但精准词条匹配一般。

###### ② 稀疏检索排序（BM25）

* 方式：基于关键词词频统计，计算 BM25 得分，分数降序排序取 top‑k
* 特点：不需要模型；擅长专有名词、数字；不懂语义同义词。

###### ③ 混合检索排序（两路融合）

把稠密检索结果、BM25 检索结果两个列表做融合重排。

两种主流融合算法：

1. **分数加权融合**：`总分数 = α*稠密分数 + β*BM25分数`，按总分排序
2. **RRF 倒数排名融合（最常用作业 / 工业）**：不直接使用原始分数，只看各自列表里的位次，把两个结果的排名换算分数再合并，对两路结果做合并重排。

> 粗排输出：拿到 10‑50 条候选 chunk，这一步允许带少量噪声。

* * *

#### 1.2 精排阶段：Reranker 重排（Cross‑Encoder 交叉模型）

---------------------------------------

###### ④ Reranker 重排排序

输入：粗排得到的候选集合。

工作：`query + chunk`拼接成对送入 Cross‑Encoder，输出 0‑1 语义相关概率，**按概率从高到低重新排序**，截取 top3‑top5 送入 LLM。

* 代表：bge‑reranker‑base
* 特点：精度最高；推理开销大，**绝对不能对全量文档跑，只对少量候选跑**。

* * *

###### 完整链路组合（工业标准）

> 文档库 →【粗排：稠密 + BM25 + RRF 融合排序】→候选 10~50 条 →【精排：Reranker 重排】→最终 top‑k 给大模型

###### 简单总结 4 种排序

1. 稠密向量余弦排序（embedding 双塔）
2. BM25 稀疏分数排序
3. 混合融合排序（RRF / 加权，合并上面两路）
4. Reranker 交叉模型语义重排（精排）

#### 3.RAG 的**自动化测试数据集构造**

     RAG 不能随便写几个问题测效果，要构造一套标准测试集，用来客观衡量你的检索召回（recall）、生成回答好不好。

##### 3.1 两种造测试集思路

* **方案 1 纯人工**：100 条问题，知识库 1000 个 chunk，人工挨个判断每个 chunk 和问题是否相关。

> 缺点：100*1000 工作量爆炸，成本太高，工业界很少这么干。

* **方案 2 AI 自动生成测试集（重点）**
  输出固定格式样本：

    {"query":"孕妇休假天数有多少？",
    "chunk":["id01","id02"],   // 要回答这个问题，必须用到的知识库块id
    "true_answer":"98天"}      // 标准答案

##### 3.2 关键设计点：按依赖 chunk 数量分层造样本

- 你的 RAG 检索配置是 `top‑k=3`，也就是最多拿回 3 个文本块。
  
  所以测试问题分三类：
  
  1. **单 chunk 问题（40%）**：只看 1 个 chunk 就能得到答案
  2. **双 chunk 问题（40%）**：必须合并 2 个 chunk 信息，才能答出来
  3. **三 chunk 问题（20%）**：要把 3 个 chunk 的信息拼在一起才能回答
  4. 四 chunk：**不要**，因为你最多检索 3 块，现实不会遇到这种 case
  
  > 为什么不能全用单 chunk？
  > 
  > 如果全部问题只需要 1 个 chunk，测出来的召回率 recall 会虚高，看起来模型很强，但真实业务里很多问题需要多处信息拼接，这个测试结果就骗了你，评估失效。

##### 3.3 前置流程

    先用 LLM 把知识库的所有 chunk 做分类整理，再按上面 40%/40%/20% 的比例，批量自动生成不同难度的 query。
    这个测试集拿来干什么？
    跑 RAG 评估：
    输入query，看 RAG 检索出来的结果，有没有命中样本标记的chunk → 算检索 Recall
    看大模型输出，和true_answer标准答案对比 → 评估生成回答质量
    一句话总结：模拟真实业务的不同难度问题，避免测试集简单导致评估结果失真，低成本做 RAG 离线评测。

    # 单chunk样本：循环50次，生成50条（占40%）
    for i in range(50):
        随机选一个分块
        llm(基于这个分块，产生一个query，和一个answer)
    
    # 双chunk样本：循环30次，生成30条（占40%）
    for i in range(30):
        随机选2个分块  # 尽量来自同一个主题库 / 同一个文档
        llm(基于这两个分块，产生一个query，和一个answer)
    
    # 三chunk样本：循环20次，生成20条（占20%）
    for i in range(20):
        随机选3个分块  # 同一个主题库或者同一个文档
        llm(基于这三个分块，产生一个query，和一个answer)

    人话翻译
    循环 50 次：每次随便挑 1 段知识库文本，丢给大模型，让模型看这段文字，自己想出一个问题 + 对应的标准答案。产出【只用 1 段就能回答】的测试样例。
    循环 30 次：一次性挑 2 段文本，给 LLM，让它结合两段的信息，想出一个必须两段合起来才能答的问题。
    举例子：A 块写产假，B 块写陪护假。生成问题：产假和陪护假分别多少天？只拿其中一段，答不全。
    循环 20 次：挑 3 段文本，LLM 融合三段信息出题。问题必须集齐三段内容，答案才完整。
    ⚠️小细节：选 2/3 个 chunk 的时候，优先从同一个文档 / 同一个主题里面挑。如果跨文档跨领域，问题会太离谱，现实业务很少出现。
    运行完，就得到 100 条我们上一页看到的那种 {query, chunk[], true_answer} 测试数据集。

#### 4 元数据 metadata

我们存入向量库的每一条 chunk，不只有`text`文本和`vector`向量，还额外带上一堆附加信息，这堆附加信息就叫**元数据**。

    {
     "text":"今天星期二。",
     "vector": [0.3243,0.8947...],  #向量
     "date":"2026‑06‑02",           #更新时间（元数据）
     "public":True,                 #是否公开（权限元数据）
     "Source":0                      #来源文档（元数据）
    }

常见元数据：更新时间、权限、文档类型、章节、来源、是否官方文档
