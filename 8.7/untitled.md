##### MCP 多顾问架构问题解读:

    工具无法保存上下文
    MCP 每个 Server 是独立进程，服务本身是无状态。每一次调用工具，MCP Server 不会记住上一轮对话；会话状态、历史记忆全部要由主客户端维护，工具之间不能直接共享记忆。
    比如交通顾问不知道景点顾问上一轮输出了哪些地点，所有信息只能由主程序传参带过去。
    async 异步锁管理
    多个 MCP 服务同时并发请求，共享同一个事件循环、LLM 调用、IO 流。会出现竞态条件：多个工具同时读写会话、同时发送 JSON‑RPC 报文，需要手动加异步锁，否则报文错乱、消息互相串扰。Windows 环境下你之前遇到的 JSON 解析报错，一部分就来源于并发 IO 冲突。
    分发决策精细化难度高
    Router 只能输出工具名字、简单参数；很难做复杂条件判断、工具依赖编排；工具调用记录很难做结构化存储，不方便日志回溯、调试。

##### 上下文通信缺陷：上下文膨胀（Token 爆炸）

    每次调用 MCP 顾问工具，主程序需要把原始用户提问、其他顾问输出结果、全部历史对话，都塞进工具请求参数传给各个 MCP 服务。
    多轮对话后 prompt 不断叠加，上下文长度持续暴涨
    Token 消耗急剧升高，带来成本上升、推理变慢
    容易超出模型上下文窗口，直接报错
    💡对比：我们的进程内旅游 demo 同样存在这个问题，属于多专家分发架构的通用痛点，不只是 MCP 独有。

##### 整合成本高

    多个工具输出结果会冲突
    不同 MCP 顾问独立生成内容，各个输出之间会出现信息矛盾。
    例子：景点顾问说 “西安酒店均价 300”，预算顾问算出来住宿 500，两套结果冲突，MCP 各个 Server 互相不知道对方输出，冲突校验、内容对齐全部交给主程序处理。
    没有内置的结果合并组件，需要自己写聚合、去重、冲突修正逻辑，开发工作量大。

##### 依赖关系与工具调用难题

    MCP 原生只支持并行独立调用工具，很难表达工具之间先后依赖。
    场景举例：必须先调用景点查询拿到地点，再调用交通工具计算路线
    MCP 本身没有编排语法，要实现串行依赖，需要主客户端做循环：调用 A → 拿到 A 结果 → 再调用 B；
    如果依赖链复杂，主程序逻辑会变得很重，相当于手写简易工作流引擎。

#### LangGraph 五大核心概念解析

> LangGraph 是基于 LangChain 的**状态机式 Agent 编排框架**，用图模型管理节点、全局状态、路由分支、并发、循环，用来解决普通 Chain 很难实现的复杂 Agent 流程。

1. State（全局状态机）

---------------

* 整个流程图**全局共享的数据容器**，所有节点都可以读取、修改里面的数据。

* Python 中一般用 `TypedDict` 定义状态的各个字段，例如：用户 query、历史对话、各个顾问返回结果、工具调用记录。

* 💡对比我们旅游 Demo：我们手动用字典在 main、scheduler 之间来回传递数据；LangGraph 把全部数据统一放到`State`，不用自己来回传参。
2. Node（节点）

-----------

* 图里面每一个执行单元就是节点，对应一个 Python 函数。

* 输入：接收当前完整`state`

* 输出：返回字典，框架会**自动合并更新到全局 state**，不需要手动写赋值。

* 对应项目映射：
  
  * 可以把 router 写成一个 node；
  * 每一个 advisor 顾问写成独立 node；
  * scheduler 聚合逻辑也可以写成 node。
3. Edge（普通边）

------------

`add_edge(A, B)`，定义节点之间固定流转关系。

* `START`：图的入口，流程从这里启动

* `END`：图的出口，走到 END 代表整个任务结束

* 普通边：A 执行完成之后，固定就跑到 B 节点，固定流向。
4. Conditional‑Edge（条件边）

------------------------

> 截图输入框是打字错误：`tong'gu` → **通过**

* **动态路由分支**：执行完上一个节点后，运行判断函数，根据 state 里面的数据，**动态决定下一个要跑哪个节点**。

* 正好可以实现我们旅游项目的 router 分发逻辑：
  
  > router 节点输出需要哪些顾问 → 条件边读取 state 中的顾问列表，动态调度对应的顾问 node。
5. 第五个概念（截图只显示 4 个，完整五大概念）

--------------------------

**Graph（图本体）**：把 state、node、edge、conditional‑edge 全部组装起来的对象，调用`.invoke(state)`启动完整流程。

#### 和你之前旅游项目的对应关系

表格

| 旅游 Demo 模块               | LangGraph 对应组件        |
| ------------------------ | --------------------- |
| main 里面的参数字典             | `State`全局状态           |
| router 路由逻辑              | 一个`Node`节点            |
| destination /budget 各个顾问 | 多个独立`Node`节点          |
| scheduler 调度选择执行哪些顾问     | `Conditional‑Edge`条件边 |
| 手动拼接汇总结果                 | 聚合`Node`              |

### 能解决前面 MCP / 多顾问的痛点

1. **状态统一托管**：不用自己到处传递 query、历史、工具返回结果，全部放在 State；
2. **原生支持分支、循环、串行依赖**：可以表达 “先跑 A，拿到结果再跑 B” 的工具依赖关系；
3. 可以很方便实现：失败重试、回退、多轮 Agent 思考；
4. 可以把 MCP 工具封装到 Graph 的 node 内部，弥补原生 MCP 不好做编排的短板。
