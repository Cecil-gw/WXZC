## 1. 方案概述

本项目 AI 部分由两条独立链路组成，二者通过"概率回写"打通：

```
链路 A（机器学习）：Excel 数据 → 特征工程 → 三算法训练 → 选优 → predict_proba → 概率回写 DB
                                                                          ↓
链路 B（大模型）  ：DB 概率 top 10% 高潜客户 → 反编码为自然语言 → Prompt → LLM → 营销邮件入库
```

| 链路 | 解决的问题 | 技术 | 输出 |
| --- | --- | --- | --- |
| A 机器学习 | 谁更可能买保险（概率排序） | LR / XGBoost / RandomForest | 每客户购买概率 |
| B 大模型 | 给高潜客户写个性化营销邮件 | qwen-flash（OpenAI 兼容协议） | 邮件 subject + content |

## 2. 机器学习技术方案

### 2.1 问题定义

- **任务类型**：二分类
- **目标**：预测客户购买车险的概率（不是 0/1 硬标签，而是连续概率用于排序）
- **正样本**：Response=1（购买），占比约 13%
- **负样本**：Response=0（不买），占比约 87%
- **不平衡比**：约 1:6.7（正:负）

### 2.2 数据集说明

采用保险交叉销售公开数据集，11 个特征 + 1 个标签：

| 特征 | 类型 | 编码策略 |
| --- | --- | --- |
| Gender | 二分类无序 | Label：Male=0, Female=1 |
| Vehicle_Damage | 二分类无序 | Label：No=0, Yes=1 |
| Vehicle_Age | 三分类**有序** | Ordinal：< 1 Year=0, 1-2 Year=1, > 2 Years=2 |
| Age / Annual_Premium / Region_Code / Policy_Sales_Channel / Vintage | 数值 | StandardScaler 标准化 |
| Driving_License / Previously_Insured | 0/1 整数 | 不处理 |

> **编码教学点**：Vehicle_Age 用 Ordinal 而非 OneHot，因为车龄有大小关系（2 > 1 > 0），OneHot 会丢掉这个先验顺序。

### 2.3 特征工程

```python
# 三种编码策略
df["Gender"] = df["Gender"].map({"Male": 0, "Female": 1})                 # Label
df["Vehicle_Damage"] = df["Vehicle_Damage"].map({"No": 0, "Yes": 1})      # Label
df["Vehicle_Age"] = df["Vehicle_Age"].map(                                # Ordinal（保留顺序）
    {"< 1 Year": 0, "1-2 Year": 1, "> 2 Years": 2}
)

# 标准化 + 分层拆分
X_train, X_test, y_train, y_test = train_test_split(X, y, stratify=y, ...)
scaler = StandardScaler()
X_train = scaler.fit_transform(X_train)  # 训练集 fit + transform
X_test  = scaler.transform(X_test)       # 测试集只 transform（防数据泄漏）
```

**关键约束**：
- `stratify=y`：保证训练/测试集正负比都是 87:13，避免测试集正样本为 0；
- `fit_transform` 只在训练集：测试集用训练集的均值/方差，否则信息泄漏。

### 2.4 模型选型与不平衡处理

三种算法各自内置不平衡处理机制，是本项目 ML 部分的核心教学点：

| 算法 | 不平衡处理参数 | 原理 | 本项目典型 ROC-AUC |
| --- | --- | --- | --- |
| LogisticRegression | `class_weight="balanced"` | sklearn 按类别频率反比自动加权 | ~0.82 |
| RandomForest | `class_weight="balanced"` | 同上 | ~0.83 |
| XGBoost | `scale_pos_weight = 负/正 ≈ 6.7` | 损失函数里放大正样本权重 | ~0.82 |

```python
# LR / RF
LogisticRegression(class_weight="balanced", ...)
RandomForestClassifier(class_weight="balanced", ...)

# XGBoost
n_neg = int((y_train == 0).sum())
n_pos = int((y_train == 1).sum())
spw = n_neg / n_pos if n_pos > 0 else 1   # ≈ 6.7
xgb.XGBClassifier(scale_pos_weight=spw, ...)
```

**为什么不用过采样/欠采样**：38 万行用 SMOTE 过采样太慢；欠采样丢数据。`class_weight` / `scale_pos_weight` 在算法层面加权，零额外开销。

### 2.5 评估指标

| 指标 | 不平衡下是否可靠 | 本项目是否采用 |
| --- | --- | --- |
| Accuracy | ❌（全猜 0 就 87%） | 不采用 |
| Precision / Recall / F1 | ⚠️ 受阈值影响 | 仅参考 |
| **ROC-AUC** | ✅ 衡量排序能力，与阈值无关 | **采用，用于选最佳模型** |

**为什么选 ROC-AUC**：营销场景要的是"把会买的人排在前面"的排序能力，AUC 衡量的正是"正样本排在负样本前面的概率"，与业务目标完全对齐。

### 2.6 模型持久化与预测一致性

**核心约束**：预测时必须复用训练时的 scaler，否则特征分布不一致 → 预测全错。

```python
# 训练时：model + scaler 一起存盘
joblib.dump({"model": model, "scaler": scaler}, f"{name}.joblib")

# 预测时：一起加载，scaler.transform（不能 fit！）
bundle = joblib.load(path)
X_new = bundle["scaler"].transform(X_new)
proba = bundle["model"].predict_proba(X_new)[:, 1]   # 取正类概率
```

**为什么 `predict_proba` 而非 `predict`**：
- `predict` 返回硬标签 [0,1,0,...]，丢失排序信息；
- `predict_proba` 返回连续概率，可按概率从高到低取 top 10%；
- 营销预算有限，要的是排序而非二分判断。

### 2.7 高潜客户筛选策略

按预测概率的**分位数**（默认 0.9 = top 10%）筛选，而非固定阈值：

```python
threshold = np.quantile(probs, 0.9)   # 90 分位数
targets = [c for c in customers if c.predicted_prob >= threshold]
```

**为什么用分位数而非固定阈值（如 0.5）**：
- 不同模型的概率分布不同（LR 偏 0.5，XGBoost 偏两端），固定 0.5 没意义；
- 用分位数保证永远取 top 10%，与模型无关，业务策略稳定。

### 2.8 评估可视化数据落库

ROC 曲线、混淆矩阵、特征重要性等可视化数据序列化成 JSON 存入 `experiments.params`，可视化接口反序列化复原图表，无需重新训练：

```python
params_json = json.dumps({
    "roc": {"fpr": fpr.tolist(), "tpr": tpr.tolist()},
    "confusion_matrix": cm.tolist(),
    "feature_importances": importances,
    "feature_names": feature_names,
})
```

## 3. 大模型技术方案

### 3.1 应用场景

为 top 10% 高潜客户**自动生成个性化营销邮件**。痛点：人工写邮件效率低、千篇一律；LLM 可根据客户画像生成有温度、有针对性的文案。

### 3.2 模型选型

| 项 | 选择 | 说明 |
| --- | --- | --- |
| 协议 | OpenAI 兼容协议 | 用官方 `openai` SDK，一行调用，自带重试 |
| 模型 | qwen-flash（通义千问） | 中文营销文案效果好、成本低、速度快 |
| 接入地址 | `LLM_API_BASE` 配置 | 换模型只改配置不改代码 |
| SDK | openai==1.51.0 | 兼容所有 OpenAI 协议服务 |

**为什么用 OpenAI SDK 而非 httpx**：SDK 封装好鉴权头、错误重试、类型校验；换厂商（OpenAI / 通义 / DeepSeek / 智谱）只需改 `base_url` + `model`。

### 3.3 Prompt 工程

Prompt 四要素：**角色设定 + 客户画像（自然语言）+ 任务要求 + 输出格式**。

```
你是保险营销文案专家。请根据以下客户画像生成一封个性化车险营销邮件。
客户画像：性别{gender}，年龄{age}岁，{driving_license}驾照，车龄{vehicle_age}，车辆{vehicle_damage}，年保费{annual_premium}元。
要求：语气专业有温度，突出该客户画像的痛点与利益，包含行动号召(CTA)。
仅返回严格 JSON，格式：{"subject":"邮件主题","content":"HTML格式正文"}
```

**关键设计**：

| 设计点 | 做法 | 原因 |
| --- | --- | --- |
| 占位符 | `{gender}` 命名占位符 + `str.format` | 模板从 DB 读，不能用 f-string（f-string 是代码期拼接） |
| 花括号转义 | 输出格式示例用 `{{ }}` | `str.format` 中 `{{` 转义为字面 `{`，保住 JSON 示例 |
| 反编码 | `driving_license=1` → "有驾照" | LLM 看自然语言不看 0/1 编码 |
| 严格 JSON 输出 | "仅返回严格 JSON" | 下游 `json.loads` 能解析，避免 markdown 包裹 |
| temperature | 0.7 | 平衡创造力（文案多样）与稳定性（格式不崩） |

### 3.4 调用链路与降级

```python
class LLMService:
    def __init__(self):
        # 没配 API_KEY 时 client=None，系统照常跑（只是邮件功能不可用）
        self.client = OpenAI(api_key=..., base_url=...) if settings.LLM_API_KEY else None

    def generate_email(self, customer, prompt_template=None):
        if not self.client:
            return {"success": False, "error": "LLM_API_KEY 未配置"}
        prompt = (prompt_template or DEFAULT_PROMPT_TEMPLATE).format(**customer_natural_lang)
        try:
            resp = self.client.chat.completions.create(
                model=settings.LLM_MODEL,
                messages=[{"role": "user", "content": prompt}],
                temperature=0.7,
            )
            content = resp.choices[0].message.content.strip()
            content = re.sub(r'^```json\s*', '', content)   # 清理 markdown 包裹
            content = re.sub(r'\s*```$', '', content)
            return {"success": True, **json.loads(content)}
        except Exception as e:
            return {"success": False, "error": str(e)}     # 降级，不抛异常拖垮业务
```

**降级策略**：
- LLM 调用失败 → 返回 `{success: False}`，业务层照常建 `email_records`（status=failed）；
- 不让 LLM 故障拖垮整个邮件生成流程，已生成的记录仍保留。

### 3.5 Prompt 模板管理

Prompt 不写死在代码里，存入 `prompt_templates` 表，运营在前端改文案不用重新部署：

```python
tpl = db.query(PromptTemplate).filter(PromptTemplate.is_active == True).first()
prompt_template = tpl.content if tpl else DEFAULT_PROMPT_TEMPLATE
```

- `is_active=True` 标记当前生效模板；
- 启动时 seed 一份默认模板兜底；
- `PUT /api/v1/email/prompt` 在线更新。

### 3.6 成本与延迟控制

| 维度 | 措施 |
| --- | --- |
| 调用量 | 只对 top 10% 高潜客户调用，不对全量 38 万调用 |
| 并发 | Flask 同步框架，邮件生成在请求线程内串行；批量生成可加后台任务 |
| 重试 | openai SDK 自带重试，无需手写 |
| 失败兜底 | 单客户失败不影响其他客户，记录 status=failed |
| 缓存 | 同一客户重复生成可加缓存（教学版未实现，列为扩展点） |

## 4. AI 与业务集成要点

### 4.1 ML → LLM 的"反编码"桥梁

ML 用 0/1 编码训练，LLM 看自然语言。两者衔接处必须把编码值反解为人类语言：

```python
# ML 编码（喂给模型）
driving_license: 1
vehicle_damage: "Yes"

# 反编码（喂给 LLM）
driving_license: "有"      # 1 → 有
vehicle_damage: "曾受损"   # Yes → 曾受损
```

这是 AI 工程化常被忽略的细节：**两个 AI 子系统之间不能直接传编码值，要经过"语义还原"**。

### 4.2 概率回写 DB 解耦训练与营销

训练与营销是两个独立请求，通过 `customers.predicted_prob` 字段解耦：

```
训练请求 → 模型存盘（.joblib）
预测请求 → 加载模型 → predict_proba → 回写 predicted_prob
邮件请求 → 查 predicted_prob → 分位筛选 → 调 LLM
```

好处：训练一次可反复预测/营销；预测结果可被多个下游消费（邮件、报表、风控）。

## 5. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 数据不平衡致模型偏向多数类 | 三算法各自不平衡处理 + ROC-AUC 选优 |
| 预测时 scaler 不一致 | model+scaler 一起 joblib.dump，预测复用 |
| LLM 输出非 JSON（带 markdown） | 正则清理 ```json 标记 + try/except 降级 |
| LLM 服务不可用 | client=None 兜底 + 单客户失败不拖垮整体 |
| 38 万行上传慢/锁库 | bulk_insert_mappings 分批 5000 条 + 每批 commit |
| Prompt 写死难迭代 | 模板入 DB，运营在线编辑 |
| 模型文件路径相对路径错 | `send_file` 用绝对路径，MODEL_DIR 用 `os.path.abspath` |
