## 1. 方案目标

- 用最小的复杂度打通「数据 → 建模 → 预测 → 营销」闭环；
- 让 ML 模型层与 LLM 调用层独立于 Web 框架，可被 CLI/后台任务复用；
- 让初学者能在 3 天内理解企业级后端的分层思想与开发流程。

---

## 2. 整体架构

本项目采用**分层架构（Layered Architecture）**，自上而下分为五层：

```
┌─────────────────────────────────────────────────────────┐
│  表现层（Presentation）  app/api/v1/*.py  + static/      │
│  Blueprint 路由 + 前端 SPA                                │
├─────────────────────────────────────────────────────────┤
│  业务层（Business）      app/services/*.py               │
│  DataService / MLService / EmailService / LLMService     │
├─────────────────────────────────────────────────────────┤
│  数据层（Data）          app/models/*.py                 │
│  6 张 ORM 表（User/Customer/Experiment/...）             │
├─────────────────────────────────────────────────────────┤
│  基础设施层（Infra）     app/core/*.py                   │
│  config / database / security / dependencies / response  │
├─────────────────────────────────────────────────────────┤
│  工具层（Utils）         app/utils/*.py                  │
│  data_processor（特征工程）/ visualizer（画图）           │
└─────────────────────────────────────────────────────────┘
```

**分层调用规则**：上层依赖下层，下层不感知上层；路由层调业务层，业务层调模型层与工具层；基础设施层被所有层共用。

## 3. 技术选型

| 分类 | 技术 | 版本 | 选型理由 |
| --- | --- | --- | --- |
| Web 框架 | Flask | 3.0.3 | 轻量、路由/蓝图清晰，适合教学；同步框架跑 CPU 密集 ML 任务天然在线程内 |
| ORM | SQLAlchemy | 2.0.30 | 原生 SQLAlchemy 2.0（不用 Flask-SQLAlchemy），模型层与框架解耦可复用 |
| 数据校验 | Pydantic | 2.7.1 | 类型注解校验请求体，自动报错，Flask 无内置校验需手动接 |
| 配置管理 | pydantic-settings | 2.2.1 | 从 .env 读配置并做类型校验，比 `app.config` 字典更安全 |
| 认证 | python-jose | 3.3.0 | JWT 签发/校验，无状态令牌利于水平扩展 |
| 密码哈希 | bcrypt | 4.1.2 | 自带盐值抗彩虹表；不经过 passlib 避免 4.x 兼容坑 |
| 数据处理 | pandas / numpy / openpyxl | — | Excel 解析、统计聚合、特征工程 |
| 机器学习 | scikit-learn / xgboost / joblib | — | LR/RF/训练评估 + 模型持久化 |
| 可视化 | matplotlib / seaborn | — | EDA 与模型评估图表，输出 base64 PNG |
| 大模型 | openai SDK | 1.51.0 | OpenAI 兼容协议一行调用，换模型只改 base_url/model |
| 前端 | Bootstrap 5 + 原生 JS | — | 单页应用，hash 路由，无构建步骤 |

## 5. 分层职责

| 层 | 目录 | 职责 | 不应做 |
| --- | --- | --- | --- |
| 表现层 | `app/api/v1/` | 接收请求、参数校验、调业务层、返回响应 | 不写复杂业务逻辑 |
| 业务层 | `app/services/` | 编排业务流程（上传入库、训练、生成邮件） | 不直接处理 HTTP |
| 数据层 | `app/models/` | 定义表结构、ORM 映射 | 不写业务逻辑 |
| 基础设施层 | `app/core/` | 配置、数据库、安全、鉴权、响应封装 | 不依赖业务层 |
| 工具层 | `app/utils/` | 特征工程、可视化等纯函数 | 不依赖业务层 |

## 6. 关键设计

### 6.1 应用工厂模式

`create_app()` 工厂函数延迟创建 Flask 实例，便于测试时切换配置、生产部署多实例：

```python
def create_app() -> Flask:
    app = Flask(__name__, static_folder="static", static_url_path="/static")
    register_blueprints(app)         # 注册蓝图
    app.teardown_appcontext(close_db) # 注册请求结束钩子
    # 注册三级异常处理器
    @app.errorhandler(BizException) ...
    @app.errorhandler(HTTPException) ...
    @app.errorhandler(Exception) ...
    with app.app_context():
        Base.metadata.create_all(bind=engine)  # 建表
        _init_admin()                           # 建 admin
        _init_prompt_template()                 # seed prompt
    return app
```

### 6.2 请求级会话管理（g + teardown）

每个 HTTP 请求开始时按需创建 DB Session 挂到 `g.db`，请求结束由 `teardown_appcontext` 钩子自动 `close()`，避免连接泄漏：

```python
def get_db():
    if "db" not in g:
        g.db = SessionLocal()
    return g.db

app.teardown_appcontext(close_db)  # 请求结束自动关
```

### 6.3 统一响应 + 业务异常

所有接口统一返回 `{code, message, data}`。业务错误不手动拼字典，而是 `raise BizException(code, message)`，由全局 `@app.errorhandler` 捕获转成统一信封。路由代码更清爽：

```python
if not user:
    raise BizException(2001, "用户不存在", 404)
```

### 6.4 RBAC 装饰器

`login_required`（登录校验）+ `role_required("admin")`（角色校验，工厂+闭包）两层装饰器，套在路由外拦截：

```python
@bp.route("/train", methods=["POST"])
@role_required("admin")
def train(): ...
```

### 6.5 配置管理（pydantic-settings）

配置以类属性声明类型与默认值，从 `.env` 覆盖，模块级实例化 `settings` 全局复用。比 `app.config` 字典更安全（类型校验、IDE 补全）。

### 6.6 模型层与框架解耦

直接用原生 SQLAlchemy 2.0（`DeclarativeBase + Mapped`），不用 Flask-SQLAlchemy 扩展。模型层可被 CLI/后台任务/测试直接复用，不被 Web 框架绑死。

### 6.7 三级异常处理优先级

`BizException`（业务）→ `HTTPException`（框架 HTTP）→ `Exception`（兜底 5000），从具体到宽泛，保证任何异常都返回统一信封而非堆栈泄露。

## 7. 数据模型设计（6 张表）

| 表 | 模型 | 说明 |
| --- | --- | --- |
| users | User | 登录账号：username/password_hash/role |
| customers | Customer | 客户数据 + predicted_prob 预测概率回写 |
| experiments | Experiment | 训练实验记录：指标 + params(JSON) + model_path + is_best |
| email_records | EmailRecord | LLM 生成的邮件正文 + status |
| operation_logs | OperationLog | 操作审计：user_id + action + details |
| prompt_templates | PromptTemplate | Prompt 模板：content + is_active |

ER 关系简述：
- `users 1 — N operation_logs`（一个用户多条操作日志）
- `customers 1 — N email_records`（一个客户多封生成邮件）
- `experiments` 单独存在，`is_best=True` 标记当前最佳模型

## 8. 安全设计

| 风险 | 对策 |
| --- | --- |
| 密码泄露 | bcrypt 哈希（带随机盐），禁止明文存储 |
| 撞库枚举用户名 | 登录失败统一返回"用户名或密码错误" |
| 越权注册 admin | 注册接口不接收 role，服务端硬编码 `user` |
| Token 伪造 | JWT 用 `JWT_SECRET_KEY` 签名，校验签名 + 过期 |
| Token 泄露 | 有效期 24h，可配置缩短；生产建议 HTTPS |
| 异常堆栈泄露 | 全局 Exception 处理器兜底，只返回 5000 业务码 |
| SQL 注入 | 全部用 ORM 或参数化 `text()`，不拼字符串 |

## 9. 与 MVC 架构的关系（重要）

> 用户问"本项目是否遵循 MVC 架构"。**诚实结论：本项目不是严格 MVC，而是分层架构**，但二者思想相通。

### 9.1 经典 MVC 三层

| 层 | 职责 | 典型技术 |
| --- | --- | --- |
| Model（模型） | 数据与业务规则 | ORM 实体 + 业务逻辑 |
| View（视图） | 渲染展示给用户 | 模板 / 前端页面 |
| Controller（控制器） | 接收请求、编排 Model、选择 View | 路由控制器 |

### 9.2 本项目分层 → MVC 的对应

| 本项目层 | 对应 MVC | 说明 |
| --- | --- | --- |
| `app/api/v1/`（路由） | Controller | 接收请求、编排业务 |
| `app/services/`（业务） | Model（业务规则部分） | 业务流程编排 |
| `app/models/`（ORM） | Model（数据部分） | 数据实体 |
| `app/static/` + JSON 响应 | View | 前端 SPA + JSON 是视图 |
| `app/core/`、`app/utils/` | （MVC 之外的基础设施） | 配置/安全/工具 |

### 9.3 为什么教学骨架要用纯 MVC

本项目把业务（services）和数据（models）拆成两层，对初学者第一次接触架构来说颗粒度偏细。**教学骨架 `insurance_mvc_starter/` 回归经典 MVC 三层**（Model/View/Controller 目录），让学员先建立最清晰的 MVC 直觉，再在 Day 2/3 过渡到主项目的分层架构，理解"分层 = MVC 的 Model 拆细 + 基础设施独立"。

## 10. 部署方案

| 环境 | 数据库 | 说明 |
| --- | --- | --- |
| 教学/开发 | SQLite | 零配置，`instance/insurance.db` 自动建 |
| 生产 | MySQL / PostgreSQL | 仅改 `DATABASE_URL`，代码无改动 |
| 模型文件 | 本地 `data/models/` | 生产可换对象存储（OSS/S3），改 `model_path` |
| LLM | 远程 API | 通过 `LLM_API_BASE` 配置，可换任意 OpenAI 兼容服务 |

启动：`python run_flask.py`，默认监听 `0.0.0.0:5000`，`debug=True` 热重载。

## 11. 扩展点

| 扩展需求 | 改动位置 | 改动量 |
| --- | --- | --- |
| 新增算法 | `ml_service._get_model` 加 `elif` 分支 | 一个分支 |
| 新增业务模块 | 新建 `api/v1/xxx.py` + 在 `register_blueprints` 注册 | 一个蓝图 |
| 换数据库 | `.env` 的 `DATABASE_URL` | 一行配置 |
| 换大模型 | `.env` 的 `LLM_API_BASE` / `LLM_MODEL` | 两行配置 |
| 加新角色 | `role_required("editor")` 装饰器直接可用 | 无需改框架 |
| 加 SMTP 发邮件 | `email_service` 加 `send` 方法 + `email_records.status` 加 sent | 一个方法 |

## 12. 与教学骨架的衔接

- 教学骨架 `insurance_mvc_starter/`（纯 MVC）实现 RBAC 登录 + 数据上传，对应 Day 1 动手部分；
- 主项目 `app/`（分层架构）是骨架"功能丰富"后的形态，Day 2/3 讲解；
- 后续功能（训练、预测、邮件、日志）通过 AI 辅助生成，从骨架生长为完整项目。
